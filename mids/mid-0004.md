# Tool 002 Create and Share Viewkey

A tool link is the magic string `monerochan`, a three-digit tool id, and underscore-delimited args, like a CLI command. MID-2 defines that structure. The browser parses these links on the page like an adblocker, intercepts the click, and runs the tool logic.

`002` asks the authenticating wallet to derive a wallet according to the slot and destination domain from the seed, configure it for scanning, and share its view key with the counterparty. The goal is a convenient webshop wallet setup that the user can recover from the seed, without fear of sharing the view key with the wrong service on recovery. (thereby being assured webshop vendor identities stay compartmentalized)

`session_start` in the actionlog (MID-2) holds the **flat payload fields** for the invocation (`toolId`, `wallet_slot`, domains, links).

```
monerochan002_create_and_share_viewkey_slot_<wallet_slot>
```

| part | meaning |
|---|---|
| `002` | tool id: create and share viewkey |
| `create_and_share_viewkey_slot` | fixed label run in the argv |
| `<wallet_slot>` | non-negative integer slot index (default `0` when building) |

Example:

```
monerochan002_create_and_share_viewkey_slot_0
```

Builder: `tools["002"].counterparty.make`.


### Parsed invocation

`parseToolInvocation` returns this object. It is the `toolCall` payload.

```json
{
  "tool": { "tool_id": "002", "payload": { "wallet_slot": 0 } },
  "destination_domain": "",
  "context_domain": "",
  "found_in": "link|linkText",
  "link": "",
  "linkText": "",
  "timestamp": 0,
  "invocation_id": "",
  "context_href": "",
  "valid": "unverified|valid|invalid"
}
```

## Stages (tool-specific)

MID-2 stages apply. This tool fills them as follows.

| stage | what 002 does |
|---|---|
| recognized | `recognize_parse`: `wallet_slot` must be an integer |
| invoked | click; `invoke_write` logs `session_start` |
| validated | same-site check; `validate_write` logs `validate_result`; `execute_deliver` opens the port |
| accepted | accept shares; dismiss refuses |
| executed | `execute_run` posts the view key; content POSTs; `execute_ok` / `execute_fail` / `execute_abort` |

## Validity

Validity runs in the content script.

`002` is valid only when:

```
context_domain equals destination_domain
```

Otherwise validity is `invalid`.

No counterparty fetch is required to settle validity.  
The tool link must be used on the same site origin as its destination (context vs destination domain per MID-2 Structure).

## Execute

On accept, the wallet UI derives the wallet from the seed via `wallet_slot` + `destination_domain`. It passes `viewkey` and `primary_address` to `actionLog.execute`. `wallet_slot` comes from the parsed invocation.

`execute_run` posts those on the port and logs `execute_start`. No port logs `execute_error`. 
The content script POSTs to the destination of the tool link only when the same-site check passed ( `context_domain` == tool link `destination_domain`):

```
POST <origin>/monerochan002/
Content-Type: application/json
```

Body:

```json
{
  "viewkey": "<viewkey>",
  "primary_address": "<primary_address>",
  "wallet_slot": <wallet_slot>
}
```

Counterparty success JSON:

```json
{
  "ok": true,
  "successUrl": "<optional url or null>"
}
```

On `ok: true` with a `successUrl`, the content script may navigate to that URL. It then sends `shareViewkeyOK`. `execute_ok` logs `execute_result`.

On failure, content sends `shareViewkeyFAILED`. `execute_fail` logs `execute_error`. The user can retry.

Port disconnect logs `aborted`.

`execute_route` rejects empty keys, bad types, and a `primary_address` that does not match an existing slot.

## Counterparty

The counterparty is the destination domain of the matching tool string.  
Because validity requires matching context domain, the page the user is on and the callback host are the same origin.

The counterparty implements `POST /monerochan002/` via `counterparty.execute_route` to receive the view-only material and may open or update a view-only wallet in `wallet_slot`.

## Privacy Implications

`002` sends view key material to the counterparty. That is intentional and sensitive.

The wallet is derived according to the wallet slot and the destination domain. The view key goes only to that service. The user can recover that wallet from the seed. Web-shop vendor identities stay compartmentalized after recovery: the keys are separated by destination domain, which prevents accidental sharing of the key with a different service programmatically. 

Constraints that meet the MID-2 privacy and compartmentalization expectation:

- validity allows the tool only when context domain equals destination domain  
- the content script opens a worker port after the validity check, **before accept**  
- the HTTP POST goes only to that origin, only after user accept (worker `shareViewkey` on the port), only on this path, and only when the same-site check passed  
- the page host is not a separate leak channel beyond that counterparty (same site rule)  
- the worker does not need a second network identity for the share POST; content keeps page identity (MID-2 zones)

Each deployment must not add extra destinations or send the view key before accept.

## Scalability Implications

`002` is an out-of-band hand-off of view material.  
The counterparty can watch the shared wallet without the authenticating user scanning for the counterparty.  

It also adds wallet slots in play (user side and counterparty side). Multi-wallet sync cost on devices still multiplies per MID-2 Scalability.

## Censorship Resistance Implications

`002` introduces no protocol-level chokepoint beyond MID-2.  
A given counterparty can still refuse `POST /monerochan002/`.  
Same-site validity means a blocked site blocks its own 002 links in context; it does not block 002 as a tool class elsewhere.
