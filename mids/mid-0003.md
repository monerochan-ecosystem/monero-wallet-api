# Tool 001 Send

A tool link is the magic string `monerochan`, a three-digit tool id, and underscore-delimited args, like a CLI command. MID-2 defines that structure. The browser parses these links on the page like an adblocker, intercepts the click, and runs the tool logic.

`001` asks the authenticating wallet to send a fixed amount to a fixed address. The default path verifies the address with the counterparty. `_no_check` skips that check. The check is GET `{origin}/monerochan001/{address}` on the destination of the tool link; only `{ "valid_address": true }` is valid, and any other body or a failed request is invalid.

`session_start` in the actionlog (MID-2) holds the **flat payload fields** for the invocation (`toolId`, `amount`, `address`, `no_check`, domains, links).


```
monerochan001_amount_<amount>_address_<address>[_no_check]
```

| part | meaning |
|---|---|
| `001` | tool id: send |
| `amount` | label; next field is the amount string |
| `<amount>` | amount in the wallet amount string form (must parse) |
| `address` | label; next field is the destination address |
| `<address>` | Monero address to pay |
| `_no_check` | optional trailing flag; skip counterparty validity GET |

Examples:

```
monerochan001_amount_0.5_address_44AFFq5kSiGBoZ4NM…
monerochan001_amount_0.5_address_44AFFq5kSiGBoZ4NM…_no_check
```

Builder: `tools["001"].counterparty.make`.  
`no_check: true` appends `_no_check`.


### Parsed invocation

`parseToolInvocation` returns this object. It is the `toolCall` payload.

```json
{
  "tool": { "tool_id": "001", "payload": { "amount": "", "address": "", "no_check": false } },
  "destination_domain": "",
  "context_domain": "",
  "found_in": "link|linkText",
  "link": "",
  "linkText": "",
  "timestamp": 0,
  "invocation_id": "",
  "context_href": "",
  "valid": "unverified|valid|invalid"
}
```

## Stages (tool-specific description)

MID-2 stages apply. This tool fills them as follows.

| stage | what 001 does |
|---|---|
| recognized | `recognize_parse`: parse `amount` and `address`; reject if amount does not parse or address is missing |
| invoked | user clicks the link; first `toolCall`; `invoke_write` logs `session_start` (flat fields) |
| validated | `validate_check`: if `no_check` stay `unverified`; else GET the counterparty origin. Second `toolCall`. `validate_write` logs `validate_result` only when `valid` is not `unverified`. `_no_check` therefore has no `validate_result` row |
| accepted | ui shows amount and address. `actionLog.execute` runs `accept_yes` then `execute_run`. `accept_no` logs `dismiss` and leaves the active list |
| executed | `execute_run`: log `execute_start`; build, sign, broadcast; log `execute_result` with `ok` true or false. No check of last type. After `dismiss`, `accept_yes` returns; `execute_run` can still send. A second `execute` can send again |

`execute_result` (including `ok: false`) leaves the active list. There is no `execute_error` type on 001.

## Validity

Validity runs in the content script on the page network identity (MID-2).

If the tool link ends with `_no_check` (`payload.no_check` is true), the wallet does **not** call the counterparty. Validity stays `unverified`. `validate_write` does not run.

Otherwise the content script requests:

```
GET <destination_domain>/monerochan001/<address>
```

`<destination_domain>` is the destination_domain of the matching tool string URL.  
`<address>` is the payload address.

Counterparty JSON:

| body | meaning |
|---|---|
| `{ "valid_address": true }` | `valid` |
| anything else, or request failure | `invalid` |

There is no domain allowlist. Only the optional `_no_check` flag skips the GET.

## Execute

`ActionLogOpened.execute` runs `accept_yes` then `execute_run`.

`execute_run` sends an ordinary Monero transfer:

- destination: payload `address` (or `args.address`)
- amount: payload `amount` (or `args.amount`); converted with `amountForChainSend`
- wallet: `args.wallet_to_send_from_pa`

`execute_run` requires an invocation row. It does **not** require an active invocation. It does **not** refuse `dismiss` or a prior `execute_result`. Fail writes `execute_result` with `ok: false` (terminal for the active list). Retry through `execute` can send again.

No required post-send callback to the counterparty is part of `001`. The counterparty can detect payment by its own scan of the chain (for example checkout session watch).

## Counterparty

The counterparty is the destination domain of the matching tool string.

It may implement `GET /monerochan001/:address` via `counterparty.validate_route` so the wallet can set validity.  
Checkout-style hosts return `valid_address: true` when that address belongs to an open session.

## Privacy Implications

The content script may call only the counterparty origin, and only for the validity GET above (never when `_no_check` is set).  
The context host (page the link was found in) is not told `toolId`, validity, or execute result by the wallet (MID-2). It does not receive communication about the link click.

The worker send is ordinary chain activity. It does not require a tool callback that names the tool to the counterparty.

Each wallet implementation of `001` must keep validity fetches limited to that GET path and must not add additional communication besides what is mentioned in the tool definition. The communication to the validity endpoint has to happen through the same content script that detected the link.
This has to happen to make sure the communication stays isolated to one circuit if the connection happened over TOR.  
`_no_check` is for cases where the issuer cannot host the check route; the user must trust the link source.


## Scalability Implications

Validity is one GET per invocation (none when `_no_check`).  
Execute is one ordinary transfer per `execute_run` call. A second call can send a second transfer.  
`001` does not add a standing channel or a global registry. No impacts on scalability.

## Censorship Resistance Implications

`001` introduces no protocol-level chokepoint beyond MID-2.
